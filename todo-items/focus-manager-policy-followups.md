# FocusManager 활성 윈도우 정책 후속 검토

## 상태와 범위

- 기록일: 2026-09-10
- 상태: TODO / 별도 검토·승인 필요. 이 문서는 즉시 구현 지시가 아니다.
- 작업 타입: 논의 후속, 코드 수정 검토, 테스트 검토
- 대상: `dali-ui-foundation/internal/focus-manager/focus-manager-impl.{cpp,h}` 및 FocusManager 자동화 테스트
- 현재 작업: 비활성 윈도우의 요청은 기존 윈도우별 기록만 갱신하고, 실제 포커스는 활성 윈도우에만 반영한다. Navigation도 해당 윈도우의 저장 위치를 사용한다.
- 제한: 기존 저장·복원 로직을 재사용한다. 아래 별도 개선을 현재 정책 수정에 일괄 포함하지 않는다.

## 1. ClearFocus의 저장 기록 보존·삭제 계약

- 타입: 설계·코드 수정 검토
- 대상: `ClearFocus`, `OnSceneHolderFocusChanged`, `OnSceneDisconnection`
- 배경: 기존 자동 focus-out은 현재 윈도우 참조를 먼저 비운 다음 ClearFocus를 호출한다. 저장 목록 삭제 조건이 일치하지 않는 부수 효과로 기록이 남는다.
- 제안: 실제 포커스 해제와 저장 기록 삭제의 계약을 명시적으로 표현한다. 저장 view와 실제 view가 다를 때도 어떤 기록을 지울지 구분한다.
- 현재 작업과의 경계: 비활성 navigation을 위해 윈도우 기준을 유지하면서 자동 해제 시 기록을 보존하는 최소 구분은 현재 정책 구현에 필요하다. 저장소 구조 재설계나 별도 API 추가는 하지 않는다.
- 미결: view 제거, 명시적 ClearFocus, 실제 포커스가 없는 상태의 ClearFocus에 대한 일관된 내부 계약과 표현 방식.
- 통합 리뷰 후속 반영: 제거·disable은 해당 view의 기록만 취소하고 다른 예약은 보존한다. 예약 대상도 scene-disconnection을 감시하며, 재부착·재활성화만으로 취소된 예약을 복원하지 않는다. 명시적 ClearFocus는 기존 합의대로 해당 윈도우 예약까지 취소한다. 더 넓은 저장소 재설계는 미결로 유지한다.
- 검증: 실제 view A와 저장 view B가 다를 때 명시적 clear, A 제거, 윈도우 focus-out을 각각 비교한다. 다른 윈도우 기록을 삭제하지 않는지 확인한다.

## 2. ClearFocus 콜백 재진입과 시그널 순서

- 타입: 별도 버그 검토
- 대상: `ClearFocus(View)`, View focus-lost 알림, `FocusChangedSignal`
- 배경: 기존 코드는 manager 시그널을 발생시킨 뒤 `mCurrentFocusView.Reset()`을 호출한다. 시그널 콜백에서 설정한 새 포커스를 바깥 ClearFocus가 다시 비울 수 있다.
- 제안: 상태 변경과 알림 순서를 검토하고, 재진입으로 설정된 포커스를 덮어쓰지 않도록 한다.
- 미결: View 알림과 manager 시그널 각각에서의 재진입, 콜백 중 getter 결과, 중첩 시그널의 순서 및 호환성.
- 현재 작업: 초기화·시그널 순서를 바꾸지 않는다.
- 검증: focus-lost 및 manager 콜백 안의 SetCurrentFocus, ClearFocus, view 제거, 윈도우 전환을 각각 테스트한다.

## 3. MoveFocusBackward의 멀티윈도우 히스토리 정책

- 타입: 정책 결정 후 코드·테스트 수정 검토
- 대상: `MoveFocusBackward`, `mFocusHistory`
- 배경: 이 API는 방향키 탐색과 별개로 전역 포커스 이력을 사용한다. 이력에 여러 윈도우의 view가 섞일 수 있다.
- 제안: 현재 윈도우 안에서만 과거 view를 찾을지, 전역 이력을 유지할지 먼저 결정한다. 저장만 한 요청을 실제 포커스 히스토리에 반영할지도 구분한다.
- 통합 리뷰 후속 반영: 단일 윈도우에서도 발생하는 반복 backward 회귀는 이번 패치에서 수정한다. setter가 이력을 다시 추가한다고 가정해 두 항목을 제거하지 않고, 선택한 항목을 유지하며 복원 시 연속 중복 추가를 방지한다. 비활성 일반 요청을 실제 이력에 일괄 추가하지 않는다. 윈도우 간 이력 선택 정책은 별도 논의로 유지한다.
- 미결: 비활성 상태에서 반복 호출할 때의 기준, 다른 윈도우 이력 보존, 저장 대상만 바뀐 경우의 히스토리 소비.
- 검증: A1 → A2 → B1 이력에서 활성·비활성 상태별 backward 결과와 다음 호출 결과를 확인한다.

## 4. 저장 view의 유효성 검사 책임

- 타입: 검증 구조 정리 검토
- 대상: 저장 view 조회, `SetCurrentFocusView`, `RequestFocus`, `DoSetCurrentFocusView`, navigation 후보 검증
- 배경: 기존 경로별 조상 차단 검사가 있다. 최종 공통 함수에 같은 조건을 무조건 추가하면 일반 setter에서는 중복 검사한다.
- 제안: 기존 검사를 재사용한다. 저장 후 다른 윈도우로 이동하거나 scene에서 제거된 경우처럼 기록 조회에 필요한 검증만 보완한다.
- 현재 작업: DoSetCurrentFocusView에 추가했던 조상 차단 중복 검사는 제외한다. 소속 윈도우 확인 및 복원 실패 시 기록 폐기는 정책 구현에 필요한 범위로 처리한다.
- 미결: 커스텀 OnFocusRequested가 반환한 view의 검증 책임, 부모의 숨김·disabled 상태, 조회와 실제 반영 사이에 발생한 상태 변경.
- 검증: 저장 후 제거·재배치·비활성화된 view와 커스텀 resolver의 다른 윈도우 반환을 비교한다.

## 5. 활성 윈도우·실제 포커스 윈도우·navigation 기준 상태

- 타입: 내부 상태 모델 정리 검토
- 대상: `mCurrentFocusedWindow`, `mCurrentWindowId`, `Window::IsFocused`, 윈도우 focus 이벤트
- 배경: false 정책에서는 실제 view가 비활성 윈도우에 남을 수 있다. 저장 위치와 OS 입력 소유권은 별개의 개념이다.
- 제안: 각 상태의 의미를 정의한 뒤 별도 멤버가 필요한지 판단한다. 정책 추가를 이유로 멤버 이름 변경·캐시 추가·ID 삭제를 한꺼번에 수행하지 않는다.
- 현재 작업: 기존 멤버를 유지하며 활성 여부는 Window 상태를 확인한다. 새 저장 요청으로 입력 소유권을 바꾸지 않는다.
- 미결: focus-in이 이전 focus-out보다 먼저 도착하는 구간, FocusManager 연결 이전의 윈도우 활성화, 사용하지 않는 ID 조회 경로 정리.
- 검증: 실제 Windows 이벤트 순서와 mock 이벤트 순서를 구분한다. DGAppSimulator 실행 검증은 사용자 요청에 따라 나중으로 미룬 상태다.

## 6. 비활성 윈도우의 touch/hover와 포커스 표시 정책

- 타입: 입력·표시 정책 결정 후 수정 검토
- 대상: `OnTouch`, `OnHover`, clear-focus-indication 옵션
- 배경: 현재 touch/hover는 실제 포커스 표시를 해제할 수 있다. 비활성 윈도우의 주입 이벤트도 이 동작을 허용할지는 포커스 요청 저장 정책과 별도다.
- 제안: 이벤트가 발생한 윈도우와 실제 포커스가 있는 윈도우의 관계를 기준으로 표시 해제 정책을 결정한다.
- 현재 작업: touch/hover의 기존 표시 정책은 변경하지 않는다. 키 navigation 후 부수적으로 현재 표시를 변경하는 경로만 비활성 저장 요청 정책과 일치시킨다.
- 미결: OS hover, FeedTouchPoint, 가상 입력, 명시적 ClearFocusIndication의 관계.
- 검증: 배경 윈도우 입력이 전경 focus ring에 미치는 영향 및 각 표시 해제 옵션 조합.
